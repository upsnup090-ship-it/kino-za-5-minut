# Расписание по слотам и админка в боте

Замена режима «окна 11:00–18:00 + 22:50, ≤3 поста в сутки» на явную сетку
день-время, которая правится из админки в личке бота.

Статус: **шаги 7 выполнены (31.10.2026), шаги 8–11 в проекте**. Решения владельца зафиксированы ниже и
обсуждению не подлежат; меняются только новым решением владельца.

---

## 1. Сетка публикаций

13 постов в неделю, время локальное (`Europe/Moscow`):

| день | слоты | постов |
|------|-------|--------|
| пн | 11:05, 20:50 | 2 |
| вт | 21:20 | 1 |
| ср | 11:05, 20:50 | 2 |
| чт | 21:20 | 1 |
| пт | 11:05, 20:50, 23:40 | 3 |
| сб | 16:40, 22:00 | 2 |
| вс | 12:00, 19:50 | 2 |
| **итого** | | **13** |

Сетка — **замена** старым окнам, а не дополнение к ним. Окна
`11:00-18:00` и `22:50`, суточный лимит `max_posts_per_day: 3` и растяжение
интервала (`effective_gap_minutes`) в режиме слотов не участвуют: каждый слот
публикует ровно один пост, и расписание само задаёт ритм.

Следствия, которые надо принять сознательно:

- Сетка окончательная, «как сказал так и делаем». Пустой день (ни одного
  слота) — допустимое состояние, не ошибка конфига.
- Самые короткие стыки: пт 23:40 → сб 16:40 (17 ч), вс 19:50 → пн 11:05
  (15 ч 15 мин). Это нормально, но на таких стыках особенно важно правило
  дедупликации по франшизе (раздел 6).
- Слот 23:40 в пятницу — это фактически ночь. Если пост не собрался за
  бюджет прогона, он не «догоняется» в 00:30, а уходит в резерв на субботу.
- Пропуск слота заметен подписчику, поэтому пустой слот обрабатывается
  резервом (раздел 5), а не молчанием.

## 2. Схема данных

SQLite, отдельная БД `data/kino.db`. `data/state.json` **не трогаем** — там
история ссылок и сигнатур (`used_links`, `used_sigs`), она работает и
переезжать не должна. Разделение осознанное: state.json — про контент,
kino.db — про расписание, резерв и журнал прогонов.

### `schedule_slots`

| колонка | тип | смысл |
|---------|-----|-------|
| `id` | INTEGER PK | |
| `weekday` | INTEGER 0..6 | 0 = понедельник, 6 = воскресенье |
| `time` | TEXT `HH:MM` | локальное время слота |
| `enabled` | INTEGER 0/1 | выключенный слот не публикует, но остаётся в таблице |
| `created_at` | TEXT ISO | |
| `updated_at` | TEXT ISO | |

День недели: **0 = понедельник**, чтобы совпадало с `datetime.weekday()` и не
требовало пересчёта на каждом чтении. В UI показываются человеческие названия
(`пн`…`вс`).

Ограничение: `UNIQUE(weekday, time)` — два слота в одну минуту одного дня
невозможны. `enabled` не входит в уникальность: выключенный и включённый слот
в одну минуту — конфликт конфигурации, а не два поста.

Первичное заполнение — из сетки раздела 1, при создании БД или явной командой
`kino schedule seed`. Повторный seed не дублирует существующие слоты
(`INSERT OR IGNORE`), но и не восстанавливает удалённые владельцем: если слот
удалён из админки, seed его не вернёт.

> Реализовано в шаге 7 (`kino/schedule_db.py`). Второе условие потребовало
> четвёртой таблицы `meta` с отметкой `seeded_at`: одного `INSERT OR IGNORE`
> мало, удалённая строка возвращается, потому что `UNIQUE(weekday, time)` для
> неё уже не срабатывает. Повторный seed — no-op; `seed_defaults(force=True)`
> в коде — осознанный повтор.

### `reserve`

Отдельная таблица, не поле в state.

| колонка | тип | смысл |
|---------|-----|-------|
| `id` | INTEGER PK | |
| `link` | TEXT UNIQUE | ссылка на материал |
| `title` | TEXT | заголовок |
| `source` | TEXT | источник |
| `format` | TEXT | формат, под который собран черновик |
| `draft_json` | TEXT | готовый черновик (уже прошедший судью) |
| `caption` | TEXT | готовая подпись |
| `image_url` | TEXT | картинка, если есть |
| `kind` | TEXT | вариация поста |
| `created_at` | TEXT ISO | когда положен в резерв |
| `expires_at` | TEXT ISO | `created_at + reserve_ttl_hours` |
| `used_at` | TEXT ISO NULL | когда взят слотом; NULL — ещё в резерве |

Так резерв видно в админке («в резерве 3 поста»), его можно вычистить одной
командой, и он не мешает истории ссылок.

### `runs`

Журнал прогонов — чтобы админка могла ответить «что было в 21:20» без чтения
логов.

| колонка | тип | смысл |
|---------|-----|-------|
| `id` | INTEGER PK | |
| `slot_id` | INTEGER NULL | какой слот сработал (NULL — ручной запуск) |
| `slot_at` | TEXT ISO | время слота по расписанию |
| `started_at` | TEXT ISO | |
| `finished_at` | TEXT ISO NULL | |
| `outcome` | TEXT | `published` \| `reserve` \| `skipped` \| `rejected` \| `failed` |
| `reason` | TEXT | почему пропуск/сбой |
| `link` | TEXT NULL | что опубликовано |
| `format` | TEXT NULL | |
| `kind` | TEXT NULL | |

Хранить 90 дней (`schedule.retention_days`, по умолчанию 90), чистить вместе с
логами.

## 3. Планировщик

### Модель исполнения: гибрид

Долгоживущий процесс `kino serve` (уже есть) + systemd `Restart=always`
(уже есть в `deploy/kino.service`) + watchdog.

Почему не systemd timer: расписание живёт в БД и правится из админки. Таймеру
пришлось бы либо перегенерировать unit-файлы на каждую правку, либо всё равно
просыпаться и читать БД — то есть вести себя как демон, но с дырками между
запусками. Демон читает слоты на каждом тике и применяет правку сразу, без
рестарта сервиса.

Что даёт гибрид:

- падение процесса лечится `Restart=always` за `RestartSec=30`;
- зависание лечится watchdog: `WatchdogSec` в юните + `sd_notify` из `serve`
  (пинг каждые `tick_seconds`), иначе systemd перезапускает процесс;
- правки расписания из админки подхватываются на следующем тике
  (`tick_seconds: 60`), рестарт не нужен.

Изменения в `deploy/kino.service`:

```ini
[Service]
Type=notify              # было simple — нужен для watchdog
WatchdogSec=180          # 3 тика; не пришёл пинг — systemd перезапускает
Restart=always
RestartSec=30
```

`Type=notify` требует, чтобы `serve` вызывал `sd_notify(READY=1)` на старте и
`sd_notify(WATCHDOG=1)` на каждом тике. Реализация — модуль `kino/notify.py`,
стандартная библиотека (`socket.AF_UNIX`, `NOTIFY_SOCKET`), без внешних
зависимостей. Если `NOTIFY_SOCKET` не задан (запуск руками, тесты) — вызовы
становятся no-op.

### Тик

Раз в `tick_seconds`:

1. Прочитать слоты из `schedule_slots` (`enabled=1`).
2. Определить, какой слот наступил: ближайший слот, время которого `<= now` и
   который ещё не отработан (`runs` не содержит `published`/`reserve`/
   `skipped` для этого `slot_id` и этой даты).
3. Если слот наступил и не отработан — прогон (раздел 4).
4. Если слот наступил, но опоздал больше `catchup_minutes` — отметить в `runs`
   как `skipped` и не пытаться снова.
5. Если слотов на сегодня больше нет — спать до ближайшего слота следующего
   дня (но не дольше `tick_seconds`, чтобы не проспать правку расписания).

Пропущенный слот не «догоняется»: если процесс лежал с 21:00 до 22:00, слот
21:20 отрабатывается при старте, но слот, который был 3 часа назад, — нет
(иначе после суток простоя бот вывалит пачку постов). Порог —
`catchup_minutes` (по умолчанию 30).

### Точность срабатывания

Тик 60 с и время `11:05`: если тик пришёлся на 11:04:50, следующая проверка —
11:05:50, минута пройдена, слот потерян до следующей недели. Поэтому слот
считается наступившим не «в эту минуту», а «в интервале
`[slot, slot + catchup_minutes)`», и отметка об отработке пишется в `runs` —
повторного срабатывания в том же слоте не будет.

### Один пост на слот

`max_posts_per_day` в режиме слотов не применяется — лимит задан самой сеткой.
`min_gap_minutes` тоже не применяется: сетка уже расставляет время. Оба
параметра остаются в конфиге только для режима `windows` (откат).

## 4. Что происходит при наступлении слота

1. Запись в `runs`: `started_at`, `slot_id`, `slot_at`, `outcome` пока пустой.
2. Обычный прогон `pipeline.run()` — сбор, выбор, черновик, судья, картинка,
   подпись.
3. Исход:
   - `published` — пост ушёл в канал. Запись `link`, `format`, `kind`.
   - `rejected` — судья отбил. Проверяем резерв (раздел 5).
   - `failed` — прогон упал (пустой сбор, все записи отфильтрованы, LLM
     недоступен, дедлайн). Проверяем резерв.
   - `skipped` — пустой слот, резерва нет (раздел 5).
4. Уведомление админу — только при `rejected`, `failed` и `skipped`. При
   успешной публикации уведомления нет: 13 постов в неделю — это 13
   сообщений, спам. Итог дня — одно сообщение в конце дня (раздел 8).

### Окно допустимости слота

Слот — это минута, но прогон идёт минутами (сбор + два LLM + картинка =
до 300 с по `run.deadline_seconds`). Поэтому:

- прогон стартует в минуту слота (или на первом тике после неё);
- публикация засчитывается слоту, если пост ушёл не позже
  `slot + late_grace_minutes` (по умолчанию 20);
- позже — пост всё равно публикуется (он готов и оплачен токенами), но
  помечается в `runs` как `published` с `reason: "опоздание N мин"`, и админу
  уходит строка в дневном итоге.

Причина: пост в 21:40 вместо 21:20 лучше, чем выброшенный пост. Но если
опоздание систематическое (LLM тормозит каждый раз), это видно в дневном итоге
и лечится бюджетом прогона, а не молчанием.

## 5. Пустой слот: резерв (A + B)

Решение владельца: **A + B вместе**. Порядок действий, когда слот наступил, а
публиковать свежее нечего:

1. **Свежий материал есть** → обычный прогон, резерв не трогаем.
2. **Свежего нет или прогон отбит** (`rejected`/`failed`) → берём из резерва
   самый старый неиспользованный пост с `expires_at > now`.
3. **Резерв пуст или всё просрочено** → слот помечается `skipped` с причиной,
   админу уходит уведомление. Сетка рвётся — это осознанно: лучше пропуск, чем
   пост двухдневной давности как «свежая новость».

Ограничения резерва:

| параметр | значение | смысл |
|----------|----------|-------|
| `reserve_max_items` | 5 | больше не держим |
| `reserve_ttl_hours` | 48 | старше — не публикуем, удаляем при чистке |

Как пост попадает в резерв: прогон собрал и опубликовал пост, а в том же
прогоне была ещё одна годная тема, которая не ушла (слот занимает один пост).
Второй черновик **не генерируется заранее** — это лишние токены на каждый
слот. В резерв попадает только то, что уже собрано и проверено судьёй, но не
опубликовано.

Следствие, которое надо принять: на практике резерв будет заполняться редко
(один пост на слот = один прогон = одна тема). Это нормально — резерв здесь
страховка от сбоя, а не основной источник. Если понадобится гарантированная
непрерывность сетки, это отдельное решение владельца: «генерировать запасной
черновик на каждый слот» (дороже в токенах) или «сдвигать слот» (ломает сетку).

## 6. Дедупликация по франшизе

При 13 постах в неделю в один день могут уйти две новости про одну франшизу
(«Оно: Добро пожаловать в Дерри» + «Пеннивайз» + «HBO Max» — в коллекции за
один прогон таких записей несколько).

Правило: **не более одного поста про одну франшизу/тайтл за
`franchise_cooldown_hours`** (по умолчанию 36).

Как определяется франшиза:

- ключевые сущности из заголовка: название фильма/сериала в кавычках, имя
  персонажа из словаря франшиз, название платформы — только в связке с
  тайтлом (одно «HBO Max» франшизой не считается);
- словарь франшиз — `config/franchises.yaml`, заполняется вручную по мере
  появления повторов; автоматическое распознавание без словаря даёт ложные
  склейки («The Batman» и «Batman Begins» — одна франшиза, а «Batman» и
  «Batman v Superman» в одном посте про разные фильмы — уже нет).

Проверка идёт в `choose.py` на этапе отбора: тема, чья франшиза публиковалась
меньше `franchise_cooldown_hours` назад, отбрасывается. Если после отбраковки
не осталось ничего — слот уходит в резерв (раздел 5).

Это не замена существующей дедупликации по ссылке и сигнатуре
(`used_links`, `used_sigs`) — она ловит ту же новость, а франшизный кулдаун
ловит разные новости про одно и то же.

## 7. Админка в боте

Инлайн, в личке с ботом, современная. Не веб-панель, не отдельный сервис — в том
же процессе `serve` (или отдельный процесс `kino admin`, решение при реализации;
в обоих случаях одна БД).

Доступ: только `ADMIN_CHAT_ID`. Любой другой чат — вежливый отказ, событие в лог.
Проверка на каждом апдейте, не только на `/start`.

Две поверхности, обе обязательны: **кнопки — основной UI**, **команды — быстрый
путь**. Команда отвечает тем же экраном с кнопками, а не отдельным текстом: два
пути к одному состоянию.

### 7.1. Ключевые приёмы

Правила, на которых держится вся админка. Нарушение любого ломает UX.

| # | Приём | Зачем |
|---|-------|-------|
| 1 | **Редактирование сообщения на месте** (`editMessageText`) вместо отправки нового | Одно сообщение — одно окно. Иначе чат забивается мусором от каждого нажатия |
| 2 | **`answerCallbackQuery` на каждое нажатие** | Иначе у кнопки навсегда остаются «часики». Тост (`text`) — для подтверждений, алерт (`show_alert`) — только для ошибок |
| 3 | **Навигационный стек** («◀️ Назад» возвращает туда, откуда пришёл) | Плоский «Назад в меню» раздражает, когда зашёл вглубь на три уровня |
| 4 | **Пространство имён в `callback_data`** + бюджет 64 байта | Иначе `slot:12:del` и `runs:2` рано или поздно столкнутся |
| 5 | **Двухшаговое подтверждение для разрушающих действий** (удалить, очистить день) | Случайный тап по «🗑» не должен сносить слот |
| 6 | **Постраничность** для «Прогонов» | 20 записей × длинная строка не влезают в лимит сообщения 4096 символов |
| 7 | **Обработка устаревших нажатий** («query is too old», «message is not modified») | Старая кнопка из истории чата не должна ронять цикл |
| 8 | **Защита от двойного тапа** (idempotency по `callback_data` + короткий таймаут) | Два быстрых нажатия «➕ Добавить» не создают два слота |
| 9 | **Проверка доступа как middleware**, а не в каждом хендлере | Одно место, нельзя забыть |
| 10 | **FSM с «Отмена» на каждом шаге и таймаутом** | Владелец ушёл — сессия не висит вечно |
| 11 | **`setMyCommands` со `scope: chat`** | Команды админки видны только в личке админа, не в канале |
| 12 | **Экранирование HTML и лимит длины** при рендере | Заголовки из фидов содержат `&`, `<`, кавычки |
| 13 | **Long polling: `allowed_updates`, `offset`, `drop_pending_updates`** | Разбор только нужных апдейтов, без отыгрыша старых после рестарта |
| 14 | **Один токен — один polling** (иначе `409 Conflict`) | Поэтому админка живёт внутри `serve`, а не отдельным процессом |

```
✅ включён   ⏸ выключен   🕓 уже отработал сегодня
```

Каждый слот — инлайн-кнопка `slot:<id>` (текст кнопки: `пн 11:05`). Нижний ряд:
`[◀️ Назад] [➕ Добавить слот] [👁 Ближайшие 7 дней]`. Команда `/schedule` →
этот экран.

#### S2 · Карточка слота

**Назначение:** всё про один слот и действия над ним.

```
🕓 пн 11:05 · включён
Последний прогон: 31.10 11:05 · опубликовано
Формат: poll · Тема: «Рамаяна»
Следующий прогон: 03.11 11:05 (через 2 дня)

[⏸ Выключить]  [✏️ Изменить время]
[🗑 Удалить]   [◀️ Назад к расписанию]
```

Колбэки: `slot:<id>:off|on`, `slot:<id>:time`, `slot:<id>:del`, `nav:sched`.
«🗑 Удалить» → подтверждение (приём 5): `Удалить слот пн 11:05?` →
`[🗑 Да, удалить] [◀️ Отмена]` (`slot:<id>:del:ok`).

#### S3 · Добавить слот — выбор дня

```
➕ Новый слот · шаг 1 из 3
Выберите день недели:

[пн] [вт] [ср] [чт] [пт] [сб] [вс]
[◀️ Отмена]
```

Колбэки: `add:day:0` … `add:day:6`, `cancel`.

#### S4 · Ввод времени (FSM)

```
➕ Новый слот · шаг 2 из 3
День: пятница
Пришлите время в формате ЧЧ:ММ (например, 23:40)
[◀️ Отмена]
```

Любой текст, кроме команды, — попытка ввода. Ошибка не выходит из состояния:
`❌ «abc» не похоже на время. Нужен формат ЧЧ:ММ, например 23:40.`

#### S5 · Подтверждение

```
➕ Проверьте слот
День: пятница
Время: 23:40
Слотов в неделю станет: 14

[✅ Добавить]  [◀️ Отмена]
```

Колбэки: `add:ok`, `cancel`.

#### S6 · Превью ближайших 7 дней

**Назначение:** последствия правок до того, как они сработают. Считается теми же
функциями, что и планировщик (одна логика, не две).

```
👁 Ближайшие 7 дней
01.11 сб 16:40 · опубликовано
01.11 сб 22:00 · впереди
03.11 пн 11:05 · впереди
03.11 пн 20:50 · впереди
…
[◀️ Назад]
```

#### S7 · Резерв

```
🗄 Резерв · 2 поста (лимит 5)
1. «Дюна: часть третья» · 31.10 10:12 · до 02.11
2. «Оскар-2027: шорт-лист» · 30.10 20:40 · до 01.11

[🧹 Вычистить просроченные]  [◀️ Назад]
```

`reserve:clean` — с подтверждением, если что-то реально удаляется.

#### S8 · Прогоны (постранично)

```
🗂 Прогоны · стр. 1 из 3
31.10 22:50 · опубликовано · poll · «Рамаяна»
31.10 11:05 · пропущен · нет материала, резерв пуст
30.10 22:50 · отклонён судьёй · выдуман факт
…
[◀️ Назад]  [◀️ Раньше]  [Позже ▶️]
```

Колбэк `runs:<page>`, страница по 8–10 записей — чтобы влезть в 4096 символов.

#### S9 · Дневной итог (push, не экран)

```
📊 Итог за 31.10
Слотов: 3 · отработано: 2 · пропущено: 1
Пропуск: 22:50 — нет материала и резерва
Токенов: 41 200 · среднее качество: 7.4/10
```

Приходит сам в конце дня. Момент отправки — открытый вопрос (раздел 10).

#### S10 · Ручной прогон

```
▶️ Запустить слот сейчас
Прогон вне сетки. Расписание и лимит дня не затрагиваются.
[▶️ Запустить]  [◀️ Отмена]
```

Если занят lock публикации: `⏳ Идёт публикация, попробуйте через минуту.`

### 7.4. Схема `callback_data` (бюджет 64 байта)

| Шаблон | Пример | Действие |
|--------|--------|----------|
| `nav:<экран>` | `nav:sched` | переход между экранами |
| `slot:<id>` | `slot:7` | карточка слота |
| `slot:<id>:<op>` | `slot:7:off` | включить/выключить |
| `slot:<id>:del:ok` | | подтверждённое удаление |
| `add:day:<0..6>` | `add:day:4` | выбран день при добавлении |
| `add:ok` / `cancel` | | подтверждение/отмена |
| `runs:<page>` | `runs:2` | страница прогонов |
| `reserve:clean` | | чистка резерва |
| `runnow:ok` | | ручной прогон |

Идентификатор слота — `schedule_slots.id` (число), **не** `weekday+time`: время
меняется, id стабилен. Любой `callback_data` валидируется (приём 4): неизвестный
префикс → тост «Кнопка устарела», без исключения.

### 7.5. Транспорт и цикл

| Параметр | Значение | Почему |
|----------|----------|--------|
| Метод | **long polling** `getUpdates` | webhook не нужен: один админ, нет публичного HTTPS-эндпоинта |
| `timeout` | 25 с | стандарт для polling, меньше нагрузки на сеть |
| `allowed_updates` | `["message","callback_query"]` | не тянем лишнее |
| `offset` | `last_update_id + 1` в памяти | персистить не нужно |
| `drop_pending_updates` | `true` на старте | иначе после рестарта отыграются старые нажатия (приём 13) |
| Поток | **отдельный от publish-loop** | пост с дедлайном 300 с не должен блокировать админку |
| Падение polling | `try/except` + перезапуск потока | не роняет публикацию (приём 14) |

### 7.6. Доступ и безопасность

Только `cfg.admin_chat_id`. Пустой `ADMIN_CHAT_ID` → **WARNING в лог, админка не
стартует**, бот публикует дальше. Проверка на каждом апдейте (middleware), чужой
чат → `⛔ Доступ только для администратора.` + запись в лог с `chat_id` (без
токена). Никаких секретов в текстах сообщений и в логах.

### 7.7. Ошибки — каждая подписана

| Ситуация | Текст пользователю | Где |
|----------|--------------------|-----|
| Не тот формат времени | `❌ Нужен формат ЧЧ:ММ, например 23:40` | S4 |
| Время вне 00:00–23:59 | `❌ Время должно быть от 00:00 до 23:59` | S4 |
| Дубль в тот же день | `❌ Такой слот уже есть: пт 23:40` | S4/S5 |
| Пустое расписание | `❌ Нельзя удалить последний слот — бот перестанет публиковать` | S1 |
| >10 слотов в день | `⚠️ Это 11 постов в неделю. Продолжить?` (не запрет) | S5 |
| Занят lock поста | `⏳ Идёт публикация, попробуйте через минуту` | S10 |
| Устаревшая кнопка | тост `Кнопка устарела, откройте расписание заново` | везде |
| Сообщение не изменилось | молча `answerCallbackQuery`, без ошибки | везде |
| Внутренняя ошибка | `⚠️ Что-то пошло не так, ошибка записана в лог` | глобально |

### 7.8. Команды (быстрый путь)

Для случаев, когда быстрее напечатать, чем нажимать:

| команда | что делает |
|---------|-----------|
| `/schedule` | экран «Расписание» с кнопками |
| `/slot add <день> <HH:MM>` | добавить слот (`/slot add пт 23:40`) |
| `/slot del <день> <HH:MM>` | удалить слот |
| `/slot on <день> <HH:MM>` | включить выключенный слот |
| `/slot off <день> <HH:MM>` | выключить слот, не удаляя |
| `/slot clear <день>` | убрать все слоты дня |
| `/next` | ближайший слот, что в резерве, что было последним |
| `/menu` | главное меню |

День принимается и сокращённо (`пн`, `вт`…), и числом (`1`–`7`, 1 =
понедельник). Ответ на любую команду — тот же экран с кнопками плюс строка «что
изменилось». Команда не заменяет кнопки: обе поверхности читают и пишут одну
таблицу `schedule_slots`, разницы в поведении нет.

### 7.9. Изменение времени и добавление слота

**Изменение времени.** Бот просит прислать `HH:MM` сообщением, валидирует,
проверяет уникальность (`weekday`, `time`), пишет в БД, отвечает «обновлено» с
кнопкой «Показать расписание». Никаких пошаговых «нажмите 1 для понедельника» —
пользователь уже в карточке слота, день известен.

**Добавление слота.** Бот просит: день (инлайн-кнопки пн…вс) → время (текстом
`HH:MM`) → подтверждение. Три шага, каждый с кнопкой «Отмена».

### 7.10. Валидация в админке

- Время: `HH:MM`, `00:00`–`23:59`. Мусор — понятная ошибка, не трейсбек.
- Дубль в один день — отказ с указанием существующего слота.
- Пустой день — разрешён (у владельца вт и чт по одному посту, но может быть и
  ноль).
- Полностью пустое расписание — отказ: бот, который никогда не публикует, это не
  конфигурация, а поломка.
- Больше 10 слотов в день — предупреждение «это N постов в неделю, уверены?» (не
  запрет).

### 7.11. Прочее в админке (не в этом этапе, но закладываем)

- «Резерв» — сколько постов, до какого числа, кнопка «вычистить просроченные».
- «Прогоны» — последние записи из `runs` с исходом и причиной.
- «Запустить слот сейчас» — ручной прогон вне сетки (для отладки).
- «Дневной итог» — одно сообщение в конце дня: сколько слотов отработано, сколько
  пропущено и почему, расход токенов.

### 7.12. Файлы, данные, тесты

**Файлы.** `kino/admin.py` — тонкий фасад (сохраняет обещание todo), вся логика в
пакете:

| файл | роль |
|------|------|
| `kino/admin.py` | цикл polling + диспетчер апдейтов |
| `kino/admin/api.py` | Telegram-транспорт (ретраи/прокси — переиспользуются из `publish.py`) |
| `kino/admin/access.py` | middleware доступа |
| `kino/admin/screens.py` | рендер экранов — **чистая функция** `state → (текст, клавиатура)` |
| `kino/admin/callbacks.py` | разбор `callback_data`, действия над БД |
| `kino/admin/session.py` | FSM + навигационный стек |
| `kino/schedule_db.py` | Шаг 7: `schedule_slots` / `reserve` / `runs` |

**Данные.** `data/kino.db`, `PRAGMA journal_mode=WAL`, соединение
`check_same_thread=False`, запись под одним `Lock`. `state.json` не трогаем.
Админка и publish-loop пишут в разные таблицы; пересечение только на `reserve` —
там lock обязателен.

**Тесты (без сети).** Рендер экранов (snapshot текста и клавиатуры), доступ
(чужой чат), валидация (время/дубль/пустой день/пустое расписание/>10), **паритет
команды и кнопки → одно состояние БД**, FSM (неверный ввод не выходит из
состояния, отмена), превью 7 дней == планировщик, занятый lock, round-trip каждого
`callback_data` и проверка ≤64 байт.

## 8. Переходный режим

Флаг в `config/settings.yaml`:

```yaml
schedule:
  mode: slots        # slots | windows
```

- `windows` — старое поведение: `schedule.windows`, `max_posts_per_day`,
  `min_gap_minutes`, `effective_gap_minutes`. Код не удаляется, остаётся
  рабочим для отката.
- `slots` — новое: сетка из `data/kino.db`, резерв, франшизный кулдаун.

Порядок перехода:

1. Создать `data/kino.db`, засидить 13 слотов (`kino schedule seed`).
2. Включить `mode: slots` в конфиге, рестарт `serve`.
3. Проверить по логу: на первом тике планировщик читает слоты из БД,
   следующий слот совпадает с сеткой.
4. Откат: `mode: windows`, рестарт. Старые окна продолжают работать,
   `kino.db` не мешает.

Старые параметры (`windows`, `max_posts_per_day`, `min_gap_minutes`) **не
удаляются** из конфига — они нужны для отката. В режиме `slots` они
игнорируются с одной строкой в логе при старте: «режим slots, окна из конфига
не используются».

`docs/automation.md` п.1 описывает старое расписание — он остаётся как история
этапа 1 и помечается ссылкой на этот файл.

## 9. Что покрыть тестами

- `schedule_slots`: чтение, `UNIQUE(weekday, time)`, seed не дублирует, seed
  не восстанавливает удалённое, `enabled=0` не публикует.
- Планировщик: слот наступил → прогон; слот отработан → второй раз не
  срабатывает; опоздание больше `catchup_minutes` → `skipped`; прогон дольше
  `late_grace_minutes` → публикация с пометкой.
- Резерв: пустой слот берёт самый старый; просроченный не берётся; после
  взятия `used_at` заполнен и повторно не берётся; больше `reserve_max_items`
  не растёт.
- Франшизный кулдаун: второй пост про ту же франшизу в пределах 36 ч
  отбрасывается; после кулдауна проходит; без словаря франшиз правило не
  срабатывает ложно.
- Админка: чужой чат получает отказ; валидация времени; дубль отклоняется;
  пустое расписание отклоняется; команда и кнопка дают одно состояние;
  превью 7 дней считает то же, что планировщик.
- Переход: `mode: windows` работает как раньше; `mode: slots` игнорирует окна;
  переключение туда-обратно не теряет слоты.

## 10. Открытые вопросы

Зафиксированы как решения, но требуют подтверждения при реализации:

1. **Отдельный процесс админки или внутри `serve`?** Внутри — проще (одна БД,
   один лог), но падение бота тянет за собой публикации. Отдельно — надёжнее,
   но два процесса и два lock. Предложение: внутри `serve` на первом этапе,
   отдельный процесс — если админка начнёт мешать циклу.
2. **`catchup_minutes = 30`** — слот, опоздавший больше, помечается `skipped`.
   При `run.deadline_seconds = 300` и `late_grace_minutes = 20` это
   согласовано, но если LLM начнёт стабильно тормозить, порог придётся
   поднимать. Смотреть в дневном итоге.
3. **Резерв почти всегда пуст** (раздел 5) — принять как есть или генерировать
   запасной черновик на каждый слот (дороже в токенах)? Решение владельца.
