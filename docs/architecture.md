# Архитектура

## Пайплайн

```
collect → choose → draft → judge → image → caption → publish
```

| Шаг | Модуль | Вход | Выход |
|-----|--------|------|-------|
| Сбор | `collect.py` / `horizon.py` | `config/sources.yaml` или дайджест Horizon | `CollectResult(items, broken, total, fresh_count)` |
| Выбор | `choose.py` | `CollectResult.items`, state | `Choice(item, format, quality_score, sad_topic)` |
| Черновик | `draft.py` | `Choice` | черновик (headline, text, key_moment, question, hashtags, карточка) |
| Судья | `judge.py` | черновик + источник | финальный текст + `verdict` (accept/reject/fallback) |
| Картинка | `image.py` | `wiki` → `film` → `director` | `ImageResult(url, title, lang)` |
| Подпись | `caption.py` | финальный текст + картинка | `caption` (лимит по вариации: 1024 или 4096) |
| Статья | `article.py` | заголовок + текст | URL страницы graph.org (Instant View) |
| Публикация | `publish.py` | `caption`, `image_url`, `kind` | выбранная вариация → фото → текст → ЛС админу |

## Вердикт судьи

Судья возвращает `verdict` одним из трёх значений, и пайплайн на них реагирует:

- **`accept`** — обычный путь, пост собирается и публикуется.
- **`reject`** — публикация отменяется. В боевом режиме ссылка записывается в
  state как использованная (иначе следующий прогон возьмёт ту же новость и
  снова упрётся в reject), админу уходит уведомление с причиной из поля
  `reason`. **В dry-run state не меняется** — это гарантия режима.
  `RunResult` возвращает `published=False`, `verdict="reject"`, пустую подпись.
  Промпт (`judge_system.txt`, `judge_user.txt`) требует заполнять `reason` при
  reject — без этого в уведомлении было «без причины».
- **`fallback`** — судья не сработал (5xx, мусор в ответе, нет модели).
  Черновик публикуется как есть, админу уходит уведомление.

Если основная модель отбилась, а `JUDGE_FALLBACK_MODEL` задан — проверка
повторяется на второй модели, и только потом ставится `fallback`.

## Подпись

Стиль один: заголовок, текст, ключевой момент, вопрос, хэштеги.

- **Обрезка безопасна для HTML.** Текст экранируется до обрезки, поэтому срез
  мог попасть внутрь сущности (`&amp;`) и Telegram отбивал пост с
  `can't parse entities`. Теперь обрезка идёт по границе блока или предложения,
  а хвост чистится от незакрытых сущностей и тегов.
- **Лимит зависит от вариации** (`caption_limit_for`): подпись к фото и
  медиагруппе — 1024 символа, текст сообщения (`text`, `link`, `poll`) — 4096.
  Раньше везде применялся общий лимит 1000, из-за чего текстовые посты резались
  без причины, а подпись к фото не имела запаса до лимита Telegram.
- **Хэштеги нормализуются** (`normalize_hashtags`): срезается ведущий `#`,
  пробелы заменяются на `_`, дубликаты убираются, мусор от модели (`None`,
  словари, числа) отбрасывается. Промпт просит теги без `#`, но модель это
  нарушает, и код подстраховывает.

## Вариации поста

Веса в `config/settings.yaml` → `post_variations`, выбор случайный:

| Вариация | Что уходит в канал |
|----------|--------------------|
| `photo` | фото с подписью |
| `link` | пост-ссылка с превью новости |
| `article` | статья на graph.org, постом-ссылкой на неё |
| `text` | текст без картинки |
| `poll` | текст поста отдельным сообщением + опрос |
| `gallery` | карусель из 2–4 фото, подпись на первом |

Веса читаются через `_safe_int`: опечатка (`photo: "35"`, `photo: много`)
логируется и считается нулём, а не роняет прогон `ValueError` после того, как
токены LLM уже потрачены. Неизвестные ключи тоже логируются.

Фолбэки: `article` без статьи → `photo`; `gallery` с <2 картинками → `photo`;
`poll` без вопроса → `photo`; `link` без ссылки → `photo`. Вариация с картинкой
без картинки (`photo`, `gallery`) уходит текстом — иначе в канал шёл текст, а в
логе было написано `gallery`.

В лог пишется вариация **после** всех фолбэков, а выбранная изначально
указывается рядом:

```
вариация поста: text (выбрана gallery, фолбэк)
```

`RunResult.kind` — что реально ушло, `RunResult.requested_kind` — что выбралось
случайно. По логу и по результату видно одно и то же.

## Статьи (вариация `article`)

Статья создаётся на **graph.org** (`api.graph.org`) — том же протоколе, что у
telegra.ph (`createAccount` / `createPage`, узлы Node в JSON). Страница
открывается в Telegram как Instant View.

- Токен: `GRAPH_TOKEN` из окружения, иначе `createAccount` и сохранение в
  `data/graph_token.txt` (атомарно).
- HTML из ответа модели (`<b>`, `&amp;`) снимается: сервис принимает в `children`
  чистый текст, иначе в статье было бы видно литеральное `<b>жирный</b>`.
- Прокси: `GRAPH_PROXY_URL`, иначе `LLM_PROXY_URL`, иначе `PROXY_URL`.
  `api.graph.org`, как и `api.telegra.ph`, напрямую из этой сети не отвечает
  (ConnectTimeout), через прокси работает штатно.
- Сетевые сбои повторяются (3 попытки), HTTP-ошибки API — нет.
- Недоступность статьи не роняет пост: `article` → фолбэк на фото.

## Источники новостей

Пайплайн поддерживает два источника, переключаются через `SOURCE_MODE`
(или `horizon.source` в `settings.yaml`):

- **`rss`** (по умолчанию) — `collect.py` тянет RSS/Atom из `config/sources.yaml`
  через `feedparser`, параллельно, с фильтром свежести.
- **`horizon`** — `horizon.py` запускает `uv run horizon --hours N`, читает
  свежий `.md` из `data/summaries/` и разбирает его в тот же список `FeedItem`.

Состав `sources.yaml`: Deadline, Variety, THR, SlashFilm, IndieWire, Guardian,
RollingStone, AVClub, Reddit, а также азиатские и российские издания —
THR/Asia, SCMP/Culture, JapanTimes/Culture, CNA/Entertainment,
Yonhap/Entertainment, InterMedia, Film.ru. YouTube-фиды убраны: они отдавали
SSLError/ReadTimeout, а RuTube закрыл RSS (404 на всех путях).

### Кэш фидов и лимиты источников

Reddit держит окно лимита около минуты, поэтому пять его фидов в один прогон
не влезают: при 429 источник берётся из последнего удачного снимка в
`data/feed_cache/` (путь меняется через `FEED_CACHE_DIR`). Без кэша 4 источника
из 5 терялись на каждом запуске. Битый кэш не выдаётся за фид.

`max_workers: 6` — общий пул для остальных источников; для Reddit применяется
последовательный проход с паузой, чтобы не упираться в лимит. Число попыток и
пауза берутся из `retry.max_attempts` / `retry.backoff_seconds`.

Оба источника отдают одинаковый тип `FeedItem(source, title, link, pub_date,
ts, snippet)`, поэтому остальной пайплайн не зависит от выбора источника.

### Horizon

Настройки в `config/settings.yaml` → `horizon`:

| Ключ | Значение по умолчанию | Смысл |
|------|----------------------|-------|
| `source` | `rss` | режим источника (`rss` \| `horizon`) |
| `dir` | `horizon` | путь к клону Horizon (относительно корня проекта) |
| `summaries_dir` | `data/summaries` | куда Horizon кладёт `.md` (относительно `dir`) |
| `run` | `true` | запускать `uv run horizon` перед чтением дайджеста |
| `hours` | `24` | окно новостей для Horizon |
| `timeout_seconds` | `600` | таймаут запуска Horizon |

Переопределить можно переменными окружения: `SOURCE_MODE`, `HORIZON_DIR`,
`HORIZON_SUMMARIES_DIR`.

Парсер `parse_digest()` разбирает Markdown-дайджест: каждая секция уровня
`##`/`###` — одна новость, заголовок — текст секции, ссылка — первая ссылка
в блоке, источник — из строки `Source:`/`来源:` или домен ссылки. Голые URL из
тела вырезаются, чтобы ссылка не попадала в snippet, а оттуда — в промпт и в
подпись. Язык определяется автоматически (EN/ZH). Если в имени файла нет даты,
`ts` берётся из mtime — иначе весь дайджест уходил в конец очереди с `ts=0`.
Если `uv` или клон Horizon отсутствуют, модуль поднимает `HorizonError` с
внятным сообщением — пайплайн не падает молча.

В `collect.py` число попыток и пауза берутся из `retry.max_attempts` /
`retry.backoff_seconds`, а не из захардкоженных значений. Записи без даты в
фиде (`ts=0`) не попадают в «свежие» — их количество пишется в лог, чтобы
«свежих нет» не выглядело проблемой источников.

## Состояние

`state.py` хранит `used_links` (до 120) и `used_sigs` (до 60) в `data/state.json`.
Запись атомарная: временный файл + `os.replace`. В dry-run state не сохраняется —
в том числе при `reject`.

Lock-файл `data/state.lock` защищает от параллельных запусков и содержит PID
владельца. Мёртвый владелец перехватывается: если процесс умер (SIGKILL, OOM,
рестарт контейнера), файл остаётся, и без проверки PID каждый следующий запуск
получал бы «другой запуск уже выполняется» — под cron это тихий отказ навсегда.
Проверяются два условия: `os.kill(pid, 0)` для владельца и возраст файла по
mtime (`STALE_AFTER_SECONDS`, по умолчанию час). Битый или пустой файл тоже
считается брошенным.

## Режимы

- `python -m kino run` — dry-run: LLM вызывается, публикации и записи state нет.
- `python -m kino run --publish` — боевой запуск.
- `python -m kino draft "тема"` — черновик по заданной теме.

Режима 24/7 (`serve`) пока нет: сейчас один запуск — один пост, расписание
задаётся внешним cron. План автоматизации и блокеры —
[`automation.md`](automation.md).

## Картинки

`image.py` ищет картинку в Wikipedia по двум эндпоинтам:

- `w/rest.php/v1/search/page` — поиск статьи по названию (limit 3);
- `api/rest_v1/page/summary/<key>` — превью по точному ключу. Это основной
  путь: у свежих фильмов поиск превью не отдаёт, хотя статья и картинка есть.

Отбор: первый результат поиска берётся как основной (Wikipedia ранжирует
сама), отбор по слову «фильм» применяется только если первая страница не
пересекается с запросом. Между запросами пауза 0.8с, 429 — повтор с
уважением к `Retry-After`. Если картинки нет — пост уходит без неё, чужая
картинка не подставляется.

Найденная картинка логируется вместе со статьёй и языком (`ImageResult.title`,
`ImageResult.lang`); если картинки нет — в лог уходят кандидаты, по которым
искали. Это нужно при разборе «картинка не та».

## Обрезка ответов LLM

`jsonparse.py` разбирает JSON из ответов модели: markdown-ограждение, текст до
и после объекта, настоящие переводы строк внутри строк, обрезанный ответ.

Когда модель упирается в `max_tokens`, объект остаётся незакрытым — тогда
включается `salvage_partial`: он достаёт значения регуляркой, и строки, и
массивы строк (без массивов терялись `hashtags` и всё, что шло после них).

Отдельный случай — reasoning-модель (`glm-5.3-flash`): весь бюджет уходит в
`reasoning_content`, `content` приходит пустым с `finish_reason=length`.
Замеры на живом API: на reasoning уходит **5900–10464 символа**
(1859–3210 completion-токенов), разброс непредсказуем, поэтому фиксированного
лимита не хватает.

`draft.py` реагирует лестницей бюджетов: базовый `max_tokens`, затем удвоенный
и потолок `_BUDGET_CEILING = 16384` (4096 → 8192 → 16384). Верхняя ступень не
ниже потолка — удвоения малого базового лимита не хватало: замеренная лестница
600 → 1200 → 1800 всё равно упиралась в стену, потому что reasoning занимает
больше. Если ответ обрезан и JSON не начался — запрос повторяется с большим
бюджетом; если JSON начался — поля спасаются без повтора. Когда не вышла ни
одна попытка, поднимается `DraftError` с указанием последнего бюджета и причины,
а `__main__.py` ловит его и уведомляет админа — без этого прогон под cron падал
необработанным исключением.

`judge.py` защищён так же (`_judge_budgets`): базовый бюджет → потолок →
фолбэк-модель. Пустой `content` при `finish_reason=length` считается провалом
попытки, а не «нет JSON» — иначе судья молча ставил бы `fallback`.

## Уведомления админу

`notify_admin` шлёт короткое сообщение в `ADMIN_CHAT_ID` и используется в двух
случаях: сбой пайплайна и отмена публикации по `reject`. Прокси отвечает через
раз (та же беда, что у graph.org), поэтому сетевые сбои повторяются до трёх раз
с паузой. HTTP-статус проверяется: 403 (бот не в чате) и 400 (неверный chat_id)
пишутся в лог, а не выглядят успешной доставкой. Уведомление никогда не роняет
пайплайн.

## Безопасность

- Секреты только из `.env` (не коммитится).
- Логи без токенов, ключей и chat_id.
- Сеть: `api.telegram.org`, `LLM_BASE_URL`, `api.graph.org` (статьи), Wikipedia (картинки), RSS-источники из `config/sources.yaml`.
