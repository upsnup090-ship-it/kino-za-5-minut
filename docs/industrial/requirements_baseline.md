## 2. Сущности и привязки

Сущности:
- **bot** — бот клиента, созданный в `@BotFather` (у каждого клиента свой).
- **user / client** — пользователь; **user_id** — уникальный Telegram ID пользователя (единственный, у каждого свой).
- **token** — токен **бота клиента из BotFather**, формат приёма мастером: **`user_id:token`**.
- **chat / channel / private_chat (личка)** — места, куда клиент добавил **своего бота** и дал **права админа**.

Правила привязки (подтверждено оператором):
- **Один клиент ↔ несколько чатов / каналов / ботов / личек** (клиент привязывает несколько мест присутствия).
- Каналы/чаты/лички — это места, куда клиент добавил своего бота с правами админа.
- Модули могут иметь разные привязки и права.
- Нужно чётко разделять данные и права: пользователь (user_id), токен бота, чат, канал, личка.

## 3. Активация бота клиента (модель B)

Схема (решение 2026-11-02):
1. Клиент в `@BotFather` создаёт **своего** бота (`/newbot`, имя, юзернейм `…_bot`), получает токен.
2. Клиент шлёт мастеру **`user_id:token`** (user_id — уникальный Telegram ID клиента).
3. Мастер **прописывает токен в `.env`** → «бот ожил» (формат: `CLIENT_<user_id>=<token>`, ключ на клиента).
4. Точка входа `pro_code/` поднимает бота клиента по конфигу и направляет его в доступные клиенту модули (по плану).
5. **Смена токена**: клиент пересоздал бота / получил новый токен → шлёт мастеру новый `user_id:token` → мастер обновляет `.env` → **старый бот «удалён»** (перестаёт работать).

Правило «без токена»: бот клиента **не активирован** (токен не прописан в `.env`) → **не работает**. Детали поведения — уточняются.

**Неактивный/битый токен** (решение 2026-11-02): при старте диспетчер проверяет токен (`getMe`); неактивный → **клиент помечается неактивным, бот недоступен**, лог мастеру; остальные боты работают (диспетчер не падает).

## 10. Данные и БД

- **2 раздельные БД единым стилем** (подтверждено): `clients.db` + `ruch.db`.
- Единый стиль = общий слой доступа к данным, единые конвенции; модули не привязаны жёстко к расположению таблиц (возможно последующее объединение в одну БД).
- Предложено (из обсуждения, **не утверждено как окончательное**): SQLite с абстрактным слоем `Database` (готовность к PostgreSQL).
- **Per-client данные** (решение 2026-11-02): расписание, резерв, статистика, повторяющиеся сообщения — **у каждого клиента свои**; таблицы привязываются к клиенту (`client_id` / `user_id`).
- **serve — вариант A** (решение 2026-11-02): один диспетчер/цикл на всех клиентов — один процесс, один тик, один лог; проверяет слоты каждого клиента и публикует в каналы его бота.
- **Всё раздельно** (решение 2026-11-02): автопостинг (Kino) остаётся со своей БД (`project/data/kino.db`) и своей логикой (слоты, runs, резерв); ручной модуль — своя БД (`ruch.db`), «в ручном всё проще». Kino **не переезжает** в `ruch.db`.

Черновик схемы (из обсуждения):

```sql
-- clients.db — клиенты, авторизация
CREATE TABLE clients (
    id INTEGER PRIMARY KEY,
    token TEXT UNIQUE NOT NULL,
    chat_id INTEGER UNIQUE,
    channel_chat_id INTEGER NOT NULL,
    username TEXT,
    role TEXT DEFAULT 'owner',      -- owner | editor | viewer
    status TEXT DEFAULT 'active',   -- active | suspended | deleted
    plan TEXT DEFAULT 'free',       -- free | auto (платный)
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- ruch.db — данные Ruch
CREATE TABLE repeating_messages (
    id INTEGER PRIMARY KEY,
    client_id INTEGER REFERENCES clients(id),
    text TEXT NOT NULL,
    time TEXT NOT NULL,
    interval_hours INTEGER DEFAULT 24,
    interval_minutes INTEGER DEFAULT 0,
    days_week TEXT DEFAULT '0,1,2,3,4,5,6',
    days_month TEXT DEFAULT '1,2,3,...,31',
    start_date TEXT,
    end_date TEXT,
    pin BOOLEAN DEFAULT FALSE,
    delete_last BOOLEAN DEFAULT FALSE,
    enabled BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE manual_posts (
    id INTEGER PRIMARY KEY,
    client_id INTEGER REFERENCES clients(id),
    channel_chat_id INTEGER NOT NULL,
    text TEXT NOT NULL,
    media_type TEXT DEFAULT 'text',  -- text | photo | document | video
    media_path TEXT,
    parse_mode TEXT DEFAULT 'HTML',
    reply_to_message_id INTEGER,
    status TEXT DEFAULT 'draft',     -- draft | sent | failed
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    sent_at TIMESTAMP
);

CREATE TABLE post_stats (
    id INTEGER PRIMARY KEY,
    post_id INTEGER REFERENCES manual_posts(id),
    client_id INTEGER REFERENCES clients(id),
    message_id INTEGER,
    views INTEGER DEFAULT 0,
    forwards INTEGER DEFAULT 0,
    reactions TEXT DEFAULT '[]',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```
