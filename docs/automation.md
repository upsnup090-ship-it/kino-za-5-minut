# План до полной автоматизации и работы 24/7

Что нужно, чтобы скрипт работал сам, круглосуточно, без человека рядом.
Каждый пункт проверен на текущем коде; формат — **что мешает → чем подтверждено
→ что сделать → как проверить**.

Сейчас: `python -m kino run --publish` — один пост за один запуск, запускается
руками или по cron. Ниже — путь до режима «поставил и забыл».

Порядок — по критичности для 24/7. Блокеры (1–4) без автоматизации не дадут
работать вообще; остальное — надёжность и удобство.

---

## Блокеры: без них 24/7 невозможно

### 1. Нет планировщика — только ручной запуск и cron

**Мешает:** в коде нет ни цикла, ни расписания. `__main__.py` знает две команды:
`run` (один пост) и `draft` (черновик по теме). Всё остальное — внешний cron,
который надо настроить руками на каждой машине.

```
$ grep -n "sub.add_parser" kino/__main__.py
35:    run_parser = sub.add_parser("run", ...)      # один пост
48:    draft_parser = sub.add_parser("draft", ...)  # черновик
# ни schedule, ни daemon, ни loop
```

**Что сделать:** команда `kino serve` — цикл, который сам решает, когда
публиковать:

- интервал между постами (`post_interval_minutes`, например 90);
- окна публикации (`active_windows: ["11:00-18:00", "22:50"]`) — не постить
  ночью; вечерний пост точечно в 22:50;
- максимум постов в сутки (`max_posts_per_day: 3`);
- пауза между попытками при сбое, без выхода из цикла;
- корректная остановка по `SIGTERM`/`SIGINT` (снять lock, дописать лог).

Счётчик постов в сутки хранить в state (`posts_today`, `last_post_at`), иначе
после рестарта цикл запостит лишнее.

**Как проверить:** `kino serve` работает сутки, в логе 2–3 публикации в окнах
11:00–18:00 и 22:50, ночью тишина, `Ctrl+C` завершает без оставшегося lock.

### 2. Прогон не укладывается в разумное время

**Мешает:** один пост может идти **минутами**. Живой замер: сбор 20+ источников
с повторами, затем два вызова LLM (черновик + судья) по 20–30с каждый, плюс
паузы к Wikipedia. Прогон, который я запускал, упирался в таймаут 500с и не
успевал.

```
$ timeout 60 python -m kino run
INFO kino.collect: источник SlashFilm: повтор через 2с (1/5)
INFO kino.collect: источник SlashFilm: повтор через 4с (2/5)
INFO kino.collect: источник SlashFilm: повтор через 6с (3/5)
EXIT=124          # убит по таймауту
```

Причина — `retry_max_attempts: 5` применяется и к сбору, и к публикации, а
`SlashFilm` отвечает медленно. Для цикла 24/7 это значит: один зависший
источник тормозит весь прогон.

**Что сделать:** общий дедлайн прогона (`run_deadline_seconds`, например 180):
сбор, LLM и публикация получают бюджет времени, по исчерпанию — мягкое
завершение с уведомлением. Отдельно — потолок на источник, чтобы один
медленный фид не съедал бюджет всех.

**Как проверить:** искусственно замедлить один источник — прогон завершается в
дедлайн, остальные шаги отрабатывают.

### 3. Логи только в stdout — под cron теряются

**Мешает:** `setup_logging()` пишет в stdout. Под cron вывод уходит в
`logs/cron.log` через `>>`, но при запуске из systemd/докера — в journald, а
при падении процесса последние строки могут не сброситься. Ротации нет: файл
растёт бесконечно.

```
$ grep -n "def setup_logging" -A 5 kino/__main__.py
def setup_logging() -> None:
    logging.basicConfig(level=logging.INFO, format=...)   # только stdout
# ни FileHandler, ни RotatingFileHandler
```

**Что сделать:** `RotatingFileHandler` на `logs/kino.log` (например 5 МБ × 5
файлов) плюс stdout для systemd. Уровень из конфига (`log_level`), чтобы
отлаживать без правки кода. Формат с временем в UTC и уровнем.

**Как проверить:** прогон оставляет `logs/kino.log`, файл ротируется при
превышении размера, старые версии сохраняются.

---

### 4. Падение процесса оставляет следы, но не сообщает о себе

**Мешает:** при `RuntimeError` (пустой сбор, все записи отфильтрованы, lock
занят) `__main__` ловит исключение и пишет в лог, но **уведомление админу**
уходит только для `DraftError` и необработанных исключений. Штатные отказы
сборки — молча.

```
$ grep -n "raise RuntimeError" kino/*.py
kino/collect.py:316: raise RuntimeError("сбор: 0 записей...")
kino/choose.py:148:  raise RuntimeError("выбор: нет записей")
kino/choose.py:159:  raise RuntimeError("выбор: все записи отфильтрованы...")
kino/pipeline.py:161: raise RuntimeError("другой запуск уже выполняется...")
```

В цикле 24/7 это значит: сутки тишины в канале, и никто не знает почему.

**Что сделать:** единая точка отчёта о прогоне — после каждого цикла админу
уходит короткий итог (опубликовано / пропущено и почему), а не только при
сбое. Плюс счётчик подряд идущих неудач: если N прогонов подряд без поста —
отдельный алерт «что-то системно сломано».

**Как проверить:** отключить один источник и испортить остальные — админ
получает «пропущено: сбор 0 записей», а не тишину.

## Надёжность: чтобы работало неделями

### 5. Нет защиты от дублей между прогонами при сбое публикации

**Мешает:** ссылка пишется в state только после успешной публикации. Если пост
ушёл в канал, а процесс упал до `save_state` (или Telegram ответил 200, а
сеть оборвалась на чтении ответа) — при следующем прогоне та же новость
выберется снова и уйдёт дублем.

```
$ grep -n "if published:" -A 12 kino/pipeline.py
if published:
    record_choice(...)      # запись только после успеха
    save_state(...)
```

**Что сделать:** писать «намерение» до публикации (двухфазная запись: пометить
ссылку как «в работе», после успеха — «опубликовано»). При старте прогона
проверять «в работе» и сверяться с каналом (последние сообщения через
`getUpdates`/`getChat`), а не публиковать вслепую.

**Как проверить:** убить процесс между `publish` и `save_state` — следующий
прогон не создаёт дубль.

---

### 6. Нет дедупликации по содержанию между днями

**Мешает:** `state_max_links: 120` и `state_max_signatures: 60` — при 3 постах
в сутки история держит ~40 дней по ссылкам и ~20 дней по сигнатурам. Этого
хватает для окна «не повторять месяц», но на грани: та же новость в другом
издании (другой URL) может пройти снова раньше.

```
config/settings.yaml:
  state_max_links: 120       # при 3 постах/сутки — 40 дней
  state_max_signatures: 60   # 20 дней
```

**Что сделать:** увеличить лимиты (ссылок 1000+, сигнатур 500+) либо перейти
на хранилище с датой (`{link, sig, ts}`) и окном «не повторять 30 дней».
Сигнатуры сейчас — мешок слов из заголовка; для устойчивости к переписанным
заголовкам стоит добавить сравнение по ключевым сущностям (название фильма,
персона), а не только по токенам.

**Как проверить:** прогнать выбор на архиве новостей за месяц — повтор не
проходит.

---

### 7. Один инстанс — нет изоляции от параллельного запуска на уровне системы

**Мешает:** защита от параллельного запуска — только файловый lock в
`data/state.lock`. Он перехватывается при мёртвом PID (это уже сделано), но
если запустить два процесса в разных контейнерах/на разных машинах с общим
`data/` — они не увидят друг друга надёжно (сетевые ФС, разные имена).

**Что сделать:** для одного хоста достаточно текущего lock + systemd
(`Restart=always`, без `Type=oneshot`). Для нескольких инстансов — вынести
state в общее хранилище с атомарной блокировкой (БД с `SELECT ... FOR UPDATE`
или Redis-лок), либо явно зафиксировать «один инстанс на канал».

**Как проверить:** два одновременных запуска — второй выходит с понятным
сообщением, дублей нет.

---

### 8. Нет бюджета на LLM — расход не контролируется

**Мешает:** каждый пост — минимум два вызова LLM (черновик + судья), плюс
повторы при обрезке (лестница бюджетов до 16384 токенов). При 3 постах в
сутки и паре-тройке повторов это копейки (расчёт выше — ~$0.05/неделю), но
учёта нет. `usage` из ответа API не читается.

```
$ grep -rn "usage" kino/*.py
# пусто — токены не считаются
```

**Что сделать:** читать `usage` из ответа и писать в `logs/format_stats.csv`
(или отдельный `logs/llm_usage.csv`): модель, prompt/completion токены, время.
Плюс мягкий лимит: при превышении недельного бюджета — пауза и уведомление
админу.

Бюджет: **50 credits MAPIMart = $5/неделю**. Реальный расход на 2.5 поста/сутки
≈ $0.05/неделю (расчёт выше), поэтому лимит-предохранитель ставим щедрым —
например $2/неделю, чтобы поймать runaway-цикл, а не штатную работу.

**Как проверить:** после суток в CSV есть расход по каждому вызову, сумма
сходится с панелью провайдера.

## Эксплуатация: чтобы можно было обслуживать

### 9. Нет healthcheck — непонятно, жив ли процесс

**Мешает:** нечем ответить на вопрос «работает ли бот сейчас». Нет ни статуса,
ни метрик, ни heartbeat.

```
$ grep -rn "health\|metrics\|/status" kino/ --include=*.py
# пусто
```

**Что сделать:** при `serve` — heartbeat-файл (`data/heartbeat.json` с
`last_run_at`, `last_post_at`, `posts_today`) и периодический пинг админу
(например, раз в сутки «жив, опубликовано N»). Внешнему мониторингу достаточно
проверять свежесть heartbeat.

**Как проверить:** остановить процесс — heartbeat устаревает, мониторинг
срабатывает.

---

### 10. Нет деплой-артефактов

**Мешает:** в репозитории нет ни `systemd`-юнита, ни `Dockerfile`, ни
`Makefile`. Каждый развёртывание — ручные шаги, которые забываются.

```
$ ls | grep -iE "docker|deploy|systemd|service|Makefile"
# пусто
```

**Что сделать:** `deploy/kino.service` (systemd: `Restart=always`,
`EnvironmentFile`, `WorkingDirectory`, лог в journald), короткий
`deploy/README.md` с шагами установки на VPS. Плюс `Makefile` с `make test`,
`make run`, `make deploy`.

Площадка — VPS, поэтому systemd-юнит основной; Dockerfile не обязателен, но
если захочешь контейнер — тот же юнит через `podman`/`docker` с
`--restart=always`.

**Как проверить:** на чистой машине установка по инструкции поднимает сервис
без ручных догадок.

---

### 11. Секреты в `.env` — при 24/7 нужна ротация и проверка на старте

**Мешает:** `load_config` падает с `ConfigError`, если ключа нет — это хорошо.
Но при долгой работе токен может протухнуть (LLM-ключ отозвали, бота
переименовали), и узнается это только по упавшему посту.

**Что сделать:** проверка связности на старте `serve`: короткий запрос к
Telegram (`getMe`) и к LLM (минимальный промпт). Если что-то не отвечает —
не стартовать и сразу сообщить админу, а не ждать первого поста.

**Как проверить:** подставить неверный `LLM_API_KEY` — сервис не стартует и
пишет внятную причину.

---

### 12. Нет тестов на длительную работу

**Мешает:** 209 тестов покрывают логику одного прогона. Ничего не проверяет
поведение цикла: счётчик постов в сутки, окна `active_windows`, восстановление
после падения, перехват lock между итерациями.

**Что сделать:** тесты на планировщик с подменённым временем (freezegun или
ручной `now`): не постит ночью, не превышает суточный лимит, после рестарта
не дублирует. Плюс тест «упал на середине — следующий цикл продолжил».

**Как проверить:** `pytest` покрывает сценарии цикла, а не только один пост.

## Порядок работ

| Этап | Пункты | Результат |
|------|--------|-----------|
| 1. Каркас 24/7 | 1, 2, 3 | `kino serve` с расписанием (окна 11:00–18:00 и 22:50, ≤3 поста/сутки), дедлайном и логами в файл — **[полная спецификация](stage1.md)** |
| 2. Наблюдаемость | 4, 9, 11 | Админ знает о сбоях и о том, что сервис жив |
| 3. Устойчивость | 5, 6, 7 | Нет дублей, история не переполняется |
| 4. Эксплуатация | 8, 10, 12 | Расход под контролем, развёртывание по инструкции, тесты цикла |

Этап 1 — минимум, чтобы включить 24/7. Этапы 2–3 — чтобы оно работало неделю
без вмешательства. Этап 4 — чтобы это можно было обслуживать и не разориться
на токенах.

## Что уже готово к 24/7

Чтобы не переделывать сделанное:

- **Lock перехватывается при мёртвом владельце** (PID + mtime) — рестарт не
  встаёт намертво. `tests/test_lock.py`.
- **Кэш фидов при 429** — источники с лимитом (Reddit) не теряются.
  `tests/test_feed_cache.py`.
- **Повторы с уважением к `retry_after`** — 429 не роняет прогон.
- **Уведомления админу с повторами** и проверкой HTTP-статуса.
  `tests/test_notify_admin.py`.
- **Reasoning-модель и бюджеты** — обрезка не роняет прогон, есть лестница до
  16384 токенов. `tests/test_draft_reasoning.py`.
- **Атомарная запись state** — падение на записи не бьёт файл.
- **Reject не публикуется**, причина уходит админу, ссылка помечается (кроме
  dry-run). `tests/test_reject_dry_run.py`.
- **Dry-run не меняет state** — можно обкатывать на боевом конфиге.

## Открытый вопрос к пользователю

Решено (ответы пользователя):

1. **Ритм публикаций.** 2–3 поста в сутки. Окна: **11:00–18:00** и **22:50**
   (точечное окно на вечерний пост).
2. **Площадка.** VPS, запуск через **systemd**.
3. **Бюджет на LLM.** 50 credits MAPIMart в неделю (= **$5**, т.к. 100 credits
   = $10).

### Расчёт бюджета

Модели: `gemini-3.8-flash` (черновик, $0.60/$3.00 за млн токенов вход/выход —
не reasoning, весь бюджет уходит на JSON), `deepseek-v4-flash` (судья,
$0.1714/$0.5143).

Один пост = 2 вызова LLM:

| Вызов | Вход | Выход | Стоимость |
|-------|------|-------|-----------|
| черновик (`gemini-3.8-flash`) | ~2500 | ~1500 | ~$0.0060 |
| судья (`deepseek-v4-flash`) | ~3500 | ~1200 | ~$0.0012 |
| **итого пост** | | | **~$0.0072** |

На 2.5 поста/сутки = 17.5 постов/неделю уходит **~$0.13/неделю** — это ~2.5% от
бюджета $5. Запас большой: даже с повторами лестницы бюджетов (до 16384
токенов) расход не приблизится к потолку.

Для сравнения: прошлая reasoning-модель `glm-5.3-flash` ($0.06/$0.20) была
в 8 раз дешевле по токенам, но тратила до 60% бюджета на скрытый reasoning и
резала черновик — экономия не стоила качества.

Вывод: лимит в пункте 8 можно ставить щедрым (например, $2/неделю как
предохранитель от runaway-цикла), реальный расход будет на порядок ниже.
