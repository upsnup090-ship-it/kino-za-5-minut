# Этап 1: каркас 24/7 — полная спецификация

Три пункта из [`automation.md`](automation.md): **1** (планировщик), **2**
(дедлайн прогона), **3** (логи в файл). Это минимум, после которого бот можно
включить на VPS и он будет работать сам.

Документ — спецификация к реализации: что пишем, какими файлами, какие
интерфейсы, что считается готовым. Код по этому документу пишется следующим
шагом.

**Решения (зафиксированы):** 2–3 поста в сутки, окна 11:00–18:00 и 22:50, VPS +
systemd, бюджет LLM $5/неделю.

---

## Что получится в конце

```bash
# на VPS, под systemd
python -m kino serve

# в логе:
# 11:02 публикация #1
# 14:37 публикация #2
# 22:50 публикация #3
# 23:00 «на сегодня лимит исчерпан, спим до 11:00»
# ночью — тишина
```

Команда `serve` не завершается: сама решает, когда постить, сама переживает
сбои, сама пишет логи в файл и корректно останавливается по `SIGTERM` от
systemd.

## Пункт 1. Планировщик `kino serve`

### 1.1. Новый модуль `kino/schedule.py`

Чистые функции без побочных эффектов — их удобно тестировать без ожидания
реального времени. Время передаётся параметром, а не берётся из `datetime.now()`
внутри, иначе тесты будут спать.

```python
"""Расписание публикаций: окна, суточный лимит, пауза между постами."""

from __future__ import annotations

from dataclasses import dataclass, field
from datetime import datetime, time, timedelta
from zoneinfo import ZoneInfo


@dataclass(frozen=True)
class Window:
    """Окно публикации: [start, end) в локальном времени.

    Точка без интервала (например 22:50) — окно нулевой длины: пост уходит
    ровно в эту минуту, а не «когда попало в течение часа».
    """
    start: time
    end: time

    @property
    def is_point(self) -> bool:
        return self.start == self.end


@dataclass
class ScheduleConfig:
    windows: list[Window]
    max_posts_per_day: int = 3
    min_gap_minutes: int = 45          # не постить два раза подряд
    tz: str = "Europe/Moscow"


@dataclass
class DayState:
    """Что уже сделано сегодня. Живёт в state, переживает рестарт."""
    date: str = ""                     # YYYY-MM-DD в локальной зоне
    posts: int = 0                     # сколько опубликовано
    last_post_at: str = ""             # ISO, локальное время


def parse_windows(raw: list[str]) -> list[Window]:
    """["11:00-18:00", "22:50"] -> [Window(11:00,18:00), Window(22:50,22:50)].

    Бросает ValueError на мусор: опечатка в конфиге должна падать на старте,
    а не превращаться в «бот молчит сутки».
    """


def next_slot(
    now: datetime,
    schedule: ScheduleConfig,
    day: DayState,
) -> datetime | None:
    """Когда можно публиковать в следующий раз.

    None — сегодня больше нельзя (лимит исчерпан или окна кончились),
    ждать до начала следующего окна следующего дня.
    """


def should_publish(now: datetime, schedule: ScheduleConfig, day: DayState) -> bool:
    """Пора ли публиковать прямо сейчас."""


def effective_gap_minutes(schedule: ScheduleConfig) -> int:
    """Интервал с учётом окна: длина_окна / постов_в_окне.

    Фиксированный минимум даёт кластеризацию — все посты в начале окна.
    """


def is_window_open(now: datetime, window: Window) -> bool:
    """Открыто ли окно в этот момент (для точечных — совпадение минуты)."""
```

**Правила, которые зашиты в функции:**

1. Если `day.date != сегодня` — счётчик сбрасывается (новый день).
2. `day.posts >= max_posts_per_day` — не публикуем.
3. `now` не попадает ни в одно окно — не публикуем.
4. С последнего поста прошло меньше `min_gap_minutes` — не публикуем.
5. Точка (`22:50`) срабатывает в минуту `22:50`, и только если лимит не
   исчерпан. Если в 22:50 бот спал — пост не «догоняется» в 23:10, окно
   считается пропущенным.
6. Окно `11:00-18:00` при `max_posts_per_day: 3` и `min_gap: 45` даёт 2–3
   поста: бот не может выстрелить три раза подряд в 11:00.
7. **Интервал растягивается под окно** (`effective_gap_minutes`). Обнаружено
   симуляцией суток: с фиксированным `min_gap: 45` бот публиковал всё к 12:30
   (`11:00, 11:45, 12:30`) и молчал до вечера — окно 420 минут использовалось
   на 90. Формула: `длина_окна / постов_в_окне`, где посты в окне =
   `max_posts_per_day - число_точек`. Для 3 постов с точкой 22:50 это
   `420 / 2 = 210` минут → `11:00, 14:30, 22:50`. Ручной `min_gap_minutes`
   остаётся жёстким полом, автоматика только растягивает.

### 1.2. Команда `serve` в `__main__.py`

```python
serve_parser = sub.add_parser("serve", help="работать 24/7: публиковать по расписанию")
serve_parser.add_argument("--dry-run", action="store_true",
                          help="не публиковать, но проходить весь цикл")
serve_parser.add_argument("--once", action="store_true",
                          help="один проход цикла и выход (для отладки)")
serve_parser.add_argument("--tick-seconds", type=int, default=60,
                          help="как часто проверять расписание")
```

`_cmd_serve(args)`:

```
1. load_config()               — ошибка конфига = выход с кодом 1, без цикла
2. setup_logging(cfg)          — логи в файл + stdout (пункт 3)
3. проверка связности          — getMe у Telegram, минимальный промпт LLM
                                 (в этапе 2 станет отдельным пунктом 11,
                                  здесь — заглушка-предупреждение в лог)
4. цикл:
     while not stopping:
         day = загрузить DayState из state
         if should_publish(now, schedule, day):
             result = run(cfg, dry_run=args.dry_run)   # один пост
             обновить DayState (posts+1, last_post_at)
             сохранить state
             отчёт в лог: опубликовано / пропущено и почему
         else:
             sleep до следующей проверки, но не дольше чем до next_slot
         if args.once: break
5. на выходе: снять lock, записать в лог «остановлен»
```

**Ключевое:** `serve` не держит lock постоянно. Lock берётся внутри `run()` на
время одного поста и отпускается. Иначе `run --publish` руками не смог бы
запуститься, пока работает `serve`.

Обработка `SIGTERM`/`SIGINT`: флаг `stopping = True`, цикл завершает текущую
итерацию и выходит. Если сигнал пришёл во время поста — пост доигрывается
(публикация не должна обрываться на середине), потом выход.

### 1.3. Поля в state

`State` расширяется, формат файла обратно совместим (старый `state.json` без
новых полей читается как «сегодня постов не было»):

```python
@dataclass
class State:
    used_links: list[str] = field(default_factory=list)
    used_sigs: list[list[str]] = field(default_factory=list)
    # --- новое для 24/7 ---
    day: str = ""              # YYYY-MM-DD локальной даты последнего поста
    posts_today: int = 0       # сколько постов в этот день
    last_post_at: str = ""     # ISO локального времени
```

`load_state` читает их с `data.get("day", "")` и т.д., `save_state` пишет.
Тесты обратной совместимости: старый файл без новых ключей грузится без ошибок.

### 1.4. Конфиг

`config/settings.yaml`, новая секция:

```yaml
schedule:
  # Окна публикации в локальном времени. "11:00-18:00" — интервал,
  # "22:50" — точное время (один пост в эту минуту).
  windows:
    - "11:00-18:00"
    - "22:50"
  max_posts_per_day: 3
  min_gap_minutes: 45
  timezone: "Europe/Moscow"
  tick_seconds: 60
```

`Settings` получает поля: `schedule_windows: list[str]`,
`max_posts_per_day: int`, `min_gap_minutes: int`, `timezone: str`,
`tick_seconds: int`. Валидация при загрузке: окна парсятся через
`parse_windows`, мусор → `ConfigError` с указанием строки.

## Пункт 2. Дедлайн прогона

### 2.1. Проблема

Сбор 20+ источников с `retry_max_attempts: 5` на каждом, затем два вызова LLM по
20–30с, затем Wikipedia с паузами. Живой замер: `timeout 60 python -m kino run`
→ `EXIT=124`, застрял на повторах SlashFilm. Один медленный фид тормозит весь
прогон, а в цикле это сдвигает расписание.

### 2.2. Решение: бюджет времени, а не жёсткий kill

Новый модуль `kino/deadline.py`:

```python
"""Бюджет времени на прогон: мягкое завершение вместо зависания."""

class Deadline:
    """Отсчитывает бюджет и умеет сказать, сколько осталось.

    Не убивает процесс (kill на середине публикации опасен), а даёт шагам
    понять, что пора закругляться.
    """

    def __init__(self, total_seconds: float):
        self.started = time.monotonic()
        self.total = total_seconds

    @property
    def elapsed(self) -> float: ...

    @property
    def remaining(self) -> float: ...

    @property
    def expired(self) -> bool: ...

    def slice(self, want: float) -> float:
        """Сколько можно потратить на шаг: min(want, remaining)."""
```

**Что меняется по шагам:**

| Шаг | Сейчас | Станет |
|-----|--------|--------|
| Сбор | 5 попыток на источник | попытки, пока есть бюджет; таймаут запроса = `slice(collect_timeout)` |
| Черновик LLM | `llm_timeout: 60` | `slice(llm_timeout)`, лестница не запускается, если бюджета нет |
| Судья | `llm_timeout: 60` | то же |
| Картинка | паузы к Wikipedia | пропускается, если бюджет исчерпан (пост уходит без картинки) |
| Публикация | — | **никогда не отменяется по дедлайну**: если пост готов, он публикуется |

Приоритет при исчерпании бюджета: **опубликовать то, что уже готово** важнее,
чем добрать картинку или пройти судью второй раз.

### 2.3. Конфиг

```yaml
run:
  deadline_seconds: 180      # общий бюджет на один пост
  collect_deadline_seconds: 90   # отдельно на сбор
```

`run()` принимает `deadline: Deadline | None = None`; если не передан —
создаёт из конфига. Обратная совместимость: `run(cfg)` работает как раньше.

### 2.4. Что при исчерпании

Не исключение, а мягкий выход: `RunResult` получает поле
`aborted: bool = False` и `abort_reason: str = ""`. `serve` видит
`aborted=True`, не считает это постом (счётчик не растёт) и логирует причину.

Если бюджет кончился **до** публикации — пост пропущен, это нормальная
ситуация, не алерт. Если три прогона подряд `aborted` — вот это алерт
(механика — этап 2, пункт 4).

## Пункт 3. Логи в файл + автоочистка (обязательно)

### 3.1. Проблема

`setup_logging()` — только `basicConfig` в stdout. Под systemd вывод уходит в
journald (нужно `journalctl -u kino`), при падении последние строки могут не
сброситься, ротации нет. При работе 24/7 лог растёт непрерывно: за месяцы он
съест диск на VPS и однажды уронит сервис.

**Автоочистка обязательна** — и по размеру, и по времени. Одного механизма мало:
ротация по размеру не спасает, если писать редко, но месяцами (файлы копятся),
а очистка по времени не спасает при аномальном всплеске логов за час.
Поэтому в этапе — оба механизма.

### 3.2. Решение: два независимых механизма

**Механизм А — ротация по размеру** (`RotatingFileHandler`): активный файл
ограничен, старые сдвигаются и удаляются по счётчику. Работает всегда, без
крона.

**Механизм Б — очистка по возрасту** (`purge_old_logs`): при старте процесса и
раз в сутки в цикле `serve` удаляются файлы логов старше `retention_days`.
Страховка от того, что ротация по размеру не покрывает — например, много
отдельных файлов (`logs/run_*.log`, `logs/pub_*.log`), которые никто не
ротирует.

```python
def setup_logging(cfg: Config | None = None, *, force_console: bool = False) -> None:
    """Логи в файл с ротацией + stdout.

    Файл: logs/kino.log, ротация по размеру (RotatingFileHandler).
    stdout оставляем: systemd/journald и ручной запуск должны видеть то же.
    Уровень из конфига (log_level), по умолчанию INFO.
    """


def purge_old_logs(
    log_dir: Path,
    *,
    retention_days: int = 14,
    max_total_bytes: int = 100 * 1024 * 1024,
    keep_names: tuple[str, ...] = ("kino.log",),
) -> list[Path]:
    """Удаляет старые логи. Возвращает список удалённых файлов.

    Два правила, применяются по порядку:

    1. По возрасту: файлы (включая ротированные `kino.log.1`) старше
       `retention_days` удаляются.
    2. По суммарному размеру: если после шага 1 каталог всё ещё больше
       `max_total_bytes`, удаляются самые старые, пока не уложимся.

    Активный файл (`kino.log`) не удаляется никогда — его держит открытым
    обработчик; ротированные версии (`kino.log.1`, `*.log.2`) удалять можно.
    Файлы, которых нет в каталоге, игнорируются. Ошибки удаления логируются,
    но не роняют процесс.
    """
```

**Почему два правила, а не одно.** Возраст ловит «редко, но долго» (месяц по
три строки в день — файл свежий по размеру, но старый по времени). Размер ловит
«много и быстро» (всплеск ошибок за час — файл молодой, но огромный). Вместе
они дают инвариант: **каталог логов не превышает `max_total_bytes` и не хранит
записи старше `retention_days`**.

### 3.3. Конфиг

```yaml
logging:
  level: INFO              # DEBUG для отладки без правки кода
  file: logs/kino.log
  max_bytes: 5242880       # 5 МБ — порог ротации активного файла
  backup_count: 5          # сколько ротированных версий держать
  console: true            # дублировать в stdout
  retention_days: 14       # старше — удалять
  max_total_bytes: 104857600   # 100 МБ на весь каталог логов
  purge_interval_hours: 24 # как часто чистить в цикле serve
```

Формат: `2026-10-18 11:02:13 INFO kino.pipeline: ...` — время локальное
(совпадает с окнами расписания, иначе неудобно сверять).

`logs/` уже в `.gitignore`, менять не нужно.

### 3.4. Когда вызывается очистка

1. **При старте** `serve` — до первого поста, чтобы старый мусор не копился.
2. **В цикле** — раз в `purge_interval_hours` (по умолчанию сутки), вместе с
   проверкой расписания.
3. **После ротации** — `RotatingFileHandler` сам удаляет лишние версии по
   `backup_count`, это механизм А.

Каждое удаление пишется в лог: сколько файлов, сколько освободилось. Молчаливое
удаление — плохо, иначе нельзя понять, куда делись логи.

### 3.5. Проверка

- После `serve` есть `logs/kino.log` с записями за прогон.
- При превышении 5 МБ появляется `logs/kino.log.1`, старые сдвигаются, лишние
  удаляются по `backup_count`.
- Файл с mtime старше `retention_days` удаляется при следующем запуске.
- Каталог, раздутый до `max_total_bytes`, ужимается до лимита (удаляются самые
  старые).
- Активный `kino.log` не удаляется никогда.
- `log_level: DEBUG` в конфиге даёт подробный вывод без правки кода.
- Тесты: `tests/test_logging.py` — ротация, удаление по возрасту, удаление по
  размеру, неприкосновенность активного файла, битый файл не роняет очистку.

## Технические предпосылки (проверены на этой машине)

Чтобы в реализации не упереться в мелочи:

- `zoneinfo.ZoneInfo("Europe/Moscow")` работает, системные tz есть
  (`/usr/share/zoneinfo/Europe/Moscow`). Пакет `tzdata` не нужен.
- `logging.handlers.RotatingFileHandler` доступен.
- `signal.SIGTERM` / `SIGINT` обрабатываются штатно.
- Python 3.12, только стандартная библиотека — новых зависимостей этап не
  добавляет.

Текущие интерфейсы, которые расширяются (проверено `inspect.signature`):

```
run(cfg: Config, dry_run: bool = True) -> RunResult     # станет deadline=None
collect(cfg: Config) -> CollectResult                   # станет deadline=None
State: used_links, used_sigs                            # + day, posts_today, last_post_at
RunResult: caption, image_url, format, published, dry_run,
           verdict, kind, requested_kind                # + aborted, abort_reason
```

В `Settings` полей расписания, дедлайна и логов сейчас нет — все новые.

## systemd-юнит (заготовка, детали — пункт 10)

```ini
[Unit]
Description=Kino za 5 minut — Telegram publisher
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=kino
WorkingDirectory=/opt/kino/project
EnvironmentFile=/opt/kino/project/.env
ExecStart=/opt/kino/project/venv/bin/python -m kino serve
Restart=always
RestartSec=30
# Мягкая остановка: serve доигрывает текущий пост и выходит
KillSignal=SIGTERM
TimeoutStopSec=120
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

`Restart=always` + `RestartSec=30`: если процесс упал, systemd поднимет его
через 30с; расписание подхватится из state, дублей не будет.

## Критерии готовности этапа

Этап закрыт, когда всё это выполняется **на живом коде**:

1. `python -m kino serve --once` проходит один цикл и выходит с кодом 0.
2. `python -m kino serve` работает сутки: в логе 2–3 публикации, все внутри
   окон 11:00–18:00 / 22:50, ночью тишина.
3. Лимит соблюдается: 4-й пост в сутки не публикуется, в логе — «лимит
   исчерпан».
4. Пауза соблюдается: два поста не уходят с разницей меньше `min_gap_minutes`.
5. Рестарт не дублирует: убить процесс после публикации, поднять снова —
   счётчик дня сохранён, пост не повторяется.
6. `SIGTERM` завершает цикл, lock не остаётся.
7. Дедлайн работает: искусственно замедленный источник — прогон завершается в
   бюджет, `RunResult.aborted=True`, причина в логе.
8. Логи: `logs/kino.log` пишется и ротируется; автоочистка работает — файл
   старше `retention_days` удаляется, раздутый каталог ужимается до
   `max_total_bytes`, активный `kino.log` остаётся; `log_level: DEBUG` работает.
9. `pytest` — все тесты проходят, включая новые на расписание и дедлайн
   (ожидается ~230+).
10. `run --publish` руками по-прежнему работает и не конфликтует с `serve`.

## Порядок реализации

Чтобы не отлаживать всё сразу:

1. `kino/schedule.py` + `tests/test_schedule.py` — чистая логика, без сети.
2. `kino/deadline.py` + `tests/test_deadline.py` — тоже чистая логика.
3. `state.py` (поля дня) + `config.py` (секции) + тесты.
4. `setup_logging(cfg)` + `purge_old_logs()` + `tests/test_logging.py`.
5. Команда `serve` в `__main__.py` с `--once` — проверка на одном цикле.
6. Дедлайн в `collect`/`draft`/`judge`/`pipeline`.
7. `deploy/kino.service` + инструкция.
8. Прогон `serve --once` на живом канале, затем сутки.
9. Документация.

## Что НЕ входит в этап 1

Чтобы не расползалось:

- **Проверка связности на старте** (пункт 11) — сейчас заглушка-предупреждение,
  полноценно в этапе 2.
- **Отчёт админу о каждом цикле и алерт после N неудач** (пункт 4) — этап 2.
- **Heartbeat и healthcheck** (пункт 9) — этап 2.
- **Учёт расхода LLM** (пункт 8) — этап 4.
- **Ротация чужих логов** (`logs/run_*.log`, `logs/pub_*.log` из старых ручных
  запусков) — `purge_old_logs` их удаляет по возрасту, но новые такие файлы
  этап 1 не создаёт.
- **Отправка логов во внешний сервис** (Loki, Sentry) — не требуется, VPS с
  systemd/journald достаточно.
- **Двухфазная запись state против дублей при сбое** (пункт 5) — этап 3.
  В этапе 1 достаточно того, что счётчик дня переживает рестарт.
- **Dockerfile** — не нужен, площадка VPS с systemd.
